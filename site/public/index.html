How it works

      
Four static scanners. No database. No upload.

      

        It reads your repo and exits non-zero if you shouldn't deploy. Everything runs on your
        machine or your CI runner — the only network calls are anonymous version lookups you can
        turn off with --offline.
      

      

        

          
01 · AST

          
Server Actions & Route Handlers

          
Parses TS/TSX with Babel and asks, per function, whether it authenticates, validates and scopes its writes — reasoning over the whole body, not a fixed window. Recognises next-safe-action wrappers.

        

        

          
02 · SQL

          
Row Level Security

          
Replays your .sql migrations in order into a model of the resulting schema, then judges the end state. Same class of check as Supabase's own linter — but static, so it runs on a pull request.

          
informed by supabase/splinter

        

        

          
03 · Registry

          
Dependency hallucination

          
Resolves every declared package against npm and PyPI for names that don't exist, freshly-registered slopsquats and typosquats — and reads install commands out of README and AGENTS.md too. Live CVEs from OSV.dev.

          
OSV.dev · slopcheck

        

        

          
04 · Secrets

          
Credentials & client boundary

          
Candidate JWTs are decoded and reported only when the payload says role: service_role. 234 patterns in all, each gated on entropy so your_api_key_here never reads as a breach.

          
gitleaks (MIT) · guardvibe (Apache-2.0)

        ClearToShip is not a replacement for Semgrep, Trivy, OSV-Scanner or TruffleHog.
        Run those too. It answers a narrower question they don't: given that an LLM wrote this,
        what did it forget? Open source, MIT-licensed, and it scans its own code on every commit.
